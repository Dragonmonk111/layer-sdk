# Incident note — 2026-10-18: overnight reboot recovery + donor findings

Context: Windows host rebooted overnight. home-vb (WSL) auto-restarted
via systemd (g1-node.service, ~40s), fell ~80k blocks behind, hit the
known rc11 catch-up wedge (D6), and force_state_sync recovery then
surfaced two new issues. Chain stayed healthy on the other 4 seats all
night.

## Findings

### D8 — donor gRPC decode cap (fixed, rc12)
`StateSyncClient` used tonic's default 4MiB decode limit; snapshot
chunk 0 is now ~7.8MiB at height ~2.22M. Every donor rejected with
`decoded message length too large` → force_state_sync crash-looped.
Fix: `max_decoding_message_size(16MiB)` on the state-sync client
(state_sync.rs). Server already encodes up to 12MiB.

### D9 — donor-side truncated block records (mitigated joiner-side; root cause open)
Some donors intermittently serve `QueryBlock` responses that are
truncated mid-varint (client decode fails before any field prints):
- vahana (57.129.103.229): regular ~every-4th-block cadence —
  2223922/26/29/33/37 all truncated from vahana, byte-identical heights
  served clean by ovh-uk1.
- ovh-uk1 (51.195.201.74): isolated heights, so far exactly the
  snapshot-donated heights (2222922, 2223927).

39-byte proposal records verified as the NORMAL form (unsigned
proposal encode — signature carried by the certificate), so this is
NOT the unsigned-proposal theory. Working hypothesis: storage-layer
torn reads around snapshot export / journal rewrite on the serving
box (vendored-storage journal territory — same family as the upstream
BlobMissing prune issue). Needs: reproduce locally, dump the stored
item bytes for a bad height on the affected box, compare journal
section state.

Joiner-side mitigation (committed): a donor serving an invalid record
is skipped (logged as evidence); `select_anchor` still enforces
`min_anchor_agree` byte-identical payloads. A corrupt donor cannot
lower the quorum bound, only fail to contribute.

### Ops gap — donor diversity
Only two seats expose gRPC 9090 (ovh-uk1 publicly, vahana publicly);
Anatoly + POSTHUMAN firewall it. With `min_anchor_agree=2` and one
flaky donor, recovery is at the mercy of which heights the snapshot
lands on. GO for rc12 asks every seat to open 9090 to the other four
seat IPs. Ravi flagged this first (2026-10-17) — confirmed correct.

## RESOLUTION — 2026-10-18 11:00 UTC

Recovery loop analysis: vahana won every "latest usable snapshot"
pick AND served an invalid record at snap+1 in all 50 attempts
(deterministic, not dice). With two donors and `min_anchor_agree=2`,
ovh-uk1 alone could never reach quorum.

One-shot recovery (documented exception, same class as force=true):
`peers = ["51.195.201.74:9090"]`, `min_anchor_agree = 1`, `force=true`
→ state-sync completed from ovh-uk1 within ~30s; home-vb resumed
finalizing at height ~2,247,000 with full 802-byte hybrid certs.
Config reverted to `force=false` immediately after; `min_anchor_agree`
returns to 2 once rc12's open-9090 ask lands (≥3 donors).

rc12 (D6+D7+D8+D9-mitigation) shipped as the release binary home-vb
ran during this recovery — sha 2d5a3b5dda6211c1…,
tag v0.6.0-rc12. D9 root cause (vahana's truncated records at a
regular cadence, ovh-uk1's at snapshot-adjacent heights) remains open
for the operators' rc12 upgrade window.

## POST-SCRIPT — D9 root cause corrected (2026-10-18 evening)

The "vahana truncated records at a regular cadence" finding was
initially misdiagnosed as a dead journal partition (frozen ≡2 mod 4
residue read as partition corruption). Three pieces of evidence
corrected it:

1. **vahana SIGNED the heights it doesn't store** — its share is in
   the cert bitmap at 2288540, so it saw that proposal live and
   voted. Nothing was written wrongly; it was never written.
2. **The residue moved** — ≡2 mod 4 at 2223xxx, ≡0 mod 4 at 2288xxx.
   Views advance ~5 per 4 heights (nullifications consume views
   without blocks), so one seat's proposal cadence lands on a
   shifting mod-4 residue. The "perfect stride" was proposer
   cadence, not storage layout.
3. **Code path**: proposal+cert are persisted ONLY inside
   `Activity::Finalization` (main.rs LayerReporter). Heights
   committed via the fast-forward path — node mid-fetch when the
   cert forms — emit no per-height Finalization activity, so
   execution stores payload but the finality record is never
   journaled. grpc.rs then serves the deliberate payload-only
   record by design.

Net: app-side write-path gap (branch coverage on fast-forwarded
finalizations), NOT vendored-storage corruption. Impact unchanged —
vahana's donor role is degraded for ~1/4 of heights — but the repair
is a cert+proposal backfill sweep from peers rather than journal
surgery, and no upstream issue is warranted. The earlier claim of
BlobMissing-family corruption is retracted.
