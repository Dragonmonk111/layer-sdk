## Incident log — 2026-10-10 certified-but-unfinalized wedge (live chain, ~4h halt)

- **Wedge**: block 312344 (payload `fdf4ab2e`) was notarized + certified by
  3/4 (bitmap `[0111]`) but **never finalized**. The payload was evicted from
  every node's in-memory `pending_payloads` before execution. Circular
  deadlock: every new view's proposal referenced a parent no node could
  execute → all certify() failed "payload unavailable" → perpetual
  nullification churn (views drained 416794→443k+).
- **Compounding**: vahana (validator-3) was down (~hours on rc1); akash-seat
  was on rc5 and also lacked the executed tip. Only 2/4 votes live.
- **Fix set shipped** (source: `commonware` @ `af1da5d`, tag `v0.6.0-rc9`):
  - rc6 — durable payload store, `ensure_executed` hook, `{data_dir}/seed/`
    loader for certified-but-unfinalized tip payloads.
  - rc7 — `halted_chain_anchor` config: state-sync may anchor on a certified
    snapshot when `snap.height+1` is not finalized.
  - rc8 — donor `block()` gRPC serves payload-only records (empty proposal +
    cert) for unfinalized heights; joiner `fetch_uncertified_tip` accepts
    them w/ `min_anchor_agree` quorum.
  - rc9 — after `adopt_snapshot`, executed tip payload injected into
    `pending_payloads` so certify() can vote on the re-proposed digest.
- **Recovery**: seed `fdf4ab2e.bin` (sha `fdf4ab2e…327e42`) installed on
  ovh+home-vb+seat; vahana self-built rc9 from the pushed tag (hash-checked —
  first DM's stale rc6 zip hashes correctly flagged by Ravi). Vahana booted
  21:16 UTC, seed executed 312344, first new finality 21:17; seat
  self-recovered (view 1→443k via in-band certs) once real finalization
  messages flowed. ~2.5 s/block, `app_hash=51165397…` consistent on all 4.
- **Lessons**: (1) in-memory pending sets are not a durability layer —
  anything certified must be durable until executed; (2) state-sync must
  tolerate certified-not-finalized tips on a halted chain (now handled);
  (3) zip hashes in DMs rot fast — point operators at the git tag instead;
  (4) an unresponsive validator (rc1-era vahana) turns a 4-of-4 incident
  into a 2-of-4 emergency.
- **Cleanup done**: temp `http.server` on ovh:8080 killed; served zips
  removed. Follow-ups → rc10 list (see below).
- **rc10 candidates**: `by_height` clobber fix; 1-peer dial limit (seen on
  home-vb AND seat logs `peers=1` — systemic, likely dial-side
  `P2pConfig`); stale akash lease addr in peer lists; resolver backfill for
  outbound-only seats (serve-send fails through Akash NAT — in-band cert
  catch-up worked, backfill didn't).
