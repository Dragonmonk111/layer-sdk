# Phase 02.2: Node Stability — fix gRPC concurrency bug and Stargate crash - Research

**Researched:** 2026-03-20
**Domain:** Rust async concurrency, gRPC/tokio Mutex contention, CosmWasm message dispatch, panic elimination
**Confidence:** HIGH

---

## Summary

Phase 02.2 is a targeted bug-fix phase addressing two concrete stability issues documented in the issue triage report and STATE.md. Both bugs are **code-level problems confirmed by direct inspection** — not speculative races or untriaged crashes. The research consisted entirely of reading the actual source files; no external documentation lookup was needed because both bugs are visible in the code.

**Bug 1 — gRPC Concurrency (#178/#162):** The `Arc<Mutex<App<T>>>` pattern is used correctly for mutual exclusion, but ALL gRPC paths (BroadcastTx, query, state sync) share a single `tokio::sync::Mutex`. Under concurrent load (`ghz` benchmarks show ~0.1% error rate) the long-held mutex during `finalize_block` (which calls the CosmWasm VM and may take 100+ ms) starves concurrent gRPC query requests. The fix is to segregate read-only query access from write access: reads need only a shared reference to `App<T>`, while writes (finalize_block, set_block_certificate) need exclusive access.

**Bug 2 — Stargate crash (#177):** The `cosmwasm_msg_to_layer()` function in `packages/app/src/wasm/keeper.rs` has `_ => todo!()` as its catch-all arm for unhandled `CosmosMsg` variants (line 1159). In CosmWasm 2.x, a contract that emits `CosmosMsg::Stargate { type_url, value }` or `CosmosMsg::Any { type_url, value }` hits this arm and panics the whole node process. The fix is to replace the `todo!()` with a graceful error return so the contract call fails cleanly instead of crashing the node.

**Primary recommendation:** Both bugs have contained, surgical fixes. Do not refactor the broader App or gRPC architecture — scope fixes narrowly to eliminate the panic and reduce mutex contention for read-only paths.

## Bug Analysis

### Bug 1: gRPC Concurrency Under Load (Issues #178 / #162)

**Location:** `app/slay3rd/src/grpc.rs` — `LayerGrpcService<T>`, `handle_cosmos_query()`

**Root cause (confirmed by code inspection):**

Every gRPC handler acquires the same `Arc<Mutex<App<T>>>`:
- `broadcast_tx` → locks `app` to call `check_tx` (sync, fast)
- `handle_cosmos_query` → locks `app` to call `app.query()` (may invoke CosmWasm VM)
- `latest_sequence` → locks `app` to call `app.latest_sequence()`
- `current_state` → locks `app` to call `app.current_state()`
- `changes_since` → locks `app` to call `app.changes_since()`

Meanwhile the consensus engine path:
- `certify()` → calls `execute_block()` → locks `app` to call `app.finalize_block()` (expensive: CosmWasm execution, RocksDB writes)
- `LayerReporter::report()` → locks `app` to call `app.set_block_certificate()` (storage write)

When `finalize_block` holds the mutex (100–500+ ms for blocks with CosmWasm contracts), all concurrent gRPC queries queue behind it. The tokio async mutex means all these tasks park on the `.await` — no CPU waste, but requests time out or accumulate, causing the ~0.1% error rate observed with `ghz`.

**Evidence of second crash vector (#162):** Multiple transactions in a single block from concurrent senders. If a `BroadcastTx` call overlaps with `finalize_block`, the sequence number check in `check_tx` may see stale state (sequence hasn't advanced yet). This is fundamentally a read-stale-state-under-contention problem.

**Fix strategy (HIGH confidence):**

Introduce a `tokio::sync::RwLock<App<T>>` for `App` access:
- Read-only operations (`query`, `info`, `latest_sequence`, `current_state`, `changes_since`, `check_tx`) acquire a shared read lock
- Write operations (`finalize_block`, `set_block_certificate`) acquire an exclusive write lock
- `check_tx` is safe as a read because it uses a `ScratchTx` (discarded after validation — no state mutation)

This allows unlimited concurrent gRPC queries while finalize_block still gets exclusive access. The `tokio::sync::RwLock` is the correct primitive because all callers are async.

**Key files to change:**
- `app/slay3rd/src/grpc.rs` — change `Arc<Mutex<App<T>>>` to `Arc<RwLock<App<T>>>`
- `app/slay3rd/src/node.rs` — change `Arc<Mutex<App<T>>>` to `Arc<RwLock<App<T>>>`
- `app/slay3rd/src/main.rs` — construct with `Arc::new(RwLock::new(app))`
- `LayerReporter` in `main.rs` — uses write lock for `set_block_certificate`

**Constraint:** `LayerNode` (in `node.rs`) also holds `Arc<Mutex<App<T>>>` and calls `finalize_block` from `execute_block`. This must be migrated in tandem. The `current_height` and `last_digest` fields in `LayerNode` can remain as `Arc<Mutex<_>>` since they are simple u64/[u8;32] values; only `App<T>` needs RwLock.

### Bug 2: Stargate / Any CosmosMsg Causes Node Crash (Issue #177)

**Location:** `packages/app/src/wasm/keeper.rs:1159` — `cosmwasm_msg_to_layer()`

**Root cause (confirmed by code inspection):**

```rust
fn cosmwasm_msg_to_layer(
    msg: CosmosMsg<super::vm::CustomMsg>,
    sender: &AccountId,
) -> Result<Msg, PulsarError> {
    let res = match msg {
        CosmosMsg::Bank(bank) => { ... }
        CosmosMsg::Wasm(wasm) => { ... }
        CosmosMsg::Custom(custom) => { ... }
        _ => todo!(),   // <-- LINE 1159: PANICS THE ENTIRE NODE PROCESS
    };
    Ok(res)
}
```

`CosmosMsg` in CosmWasm 2.x has additional variants beyond Bank/Wasm/Custom:
- `CosmosMsg::Stargate { type_url: String, value: Binary }` — raw protobuf message dispatch
- `CosmosMsg::Any { type_url: String, value: Binary }` — IBC-style any message
- `CosmosMsg::Gov(...)` — governance messages (staking proposals, etc.)
- `CosmosMsg::Distribution(...)` — distribution messages
- `CosmosMsg::IbcMsg(...)` — IBC messages

When a WASM contract emits any of these (e.g., a DAO governance proposal with `MsgInstantiateContract` inside a Stargate message, as described in issue #177), `cosmwasm_msg_to_layer()` hits `todo!()` and panics. The panic propagates through the CosmWasm VM call stack, through `finalize_block`, through `execute_block`, through the `certify()` callback into the Commonware consensus engine. Since the engine does not catch panics, the OS process terminates.

**Additional panic sites in the same function:**
- Line 1039: `x => unimplemented!("bank msg {:?}", x)` — triggers on `BankMsg::Delegate` or future variants
- Line 1110: `x => unimplemented!("wasm msg {:?}", x)` — triggers on future `WasmMsg` variants

**Fix strategy (HIGH confidence):**

Replace all `todo!()` and `unimplemented!()` arms in `cosmwasm_msg_to_layer()` with graceful `Err(PulsarError::...)` returns. The contract execution will fail cleanly, the transaction will be marked as failed in the block, and the node continues running.

Define a new `PulsarError` variant (or reuse an existing one):
```rust
// Suggested new variant in error.rs:
UnsupportedMessage { type_name: String },
```

Then replace:
```rust
// BEFORE (panics):
_ => todo!(),

// AFTER (graceful error):
other => return Err(PulsarError::UnsupportedMessage {
    type_name: format!("{:?}", std::mem::discriminant(&other)),
}),
```

Apply the same pattern to the `unimplemented!()` arms on lines 1039 and 1110.

**Also relevant:** `packages/cosmos/src/query.rs:85` has `"version" => todo!()` in `parse_app_query()`. If a query hits this path it will also crash. Should be fixed to return `QueryError::UnsupportedPath`.

## Architecture Patterns

### Pattern 1: RwLock Migration Pattern for App<T>

**What:** Replace `Arc<Mutex<App<T>>>` with `Arc<RwLock<App<T>>>` to allow concurrent reads while protecting writes.

**When to use:** When one expensive writer (finalize_block) must not block many cheap readers (gRPC queries).

**Type aliases to define in grpc.rs:**
```rust
// Before:
pub struct LayerGrpcService<T: PersistentStorage + Send + Sync + 'static> {
    pub app: Arc<Mutex<App<T>>>,
    ...
}

// After:
pub struct LayerGrpcService<T: PersistentStorage + Send + Sync + 'static> {
    pub app: Arc<RwLock<App<T>>>,
    ...
}
```

**Read-only paths (use `.read().await`):**
```rust
// broadcast_tx — check_tx is read-only (ScratchTx, no mutation)
let check = {
    let app = self.app.read().await;
    if app.info().is_none() {
        return Err(Status::unavailable("node initializing"));
    }
    app.check_tx(tx)
};

// handle_cosmos_query
let response = {
    let app = app.read().await;
    app.query(query)
};
```

**Write paths (use `.write().await`):**
```rust
// execute_block in node.rs — finalize_block mutates state
let result = {
    let mut app = self.app.write().await;
    app.finalize_block(block)
};

// LayerReporter::report — set_block_certificate mutates state
let mut app = self.app.write().await;
app.set_block_certificate(height, cert_bytes)
```

### Pattern 2: Graceful Error Return Pattern for Unimplemented Messages

**What:** Replace `todo!()`/`unimplemented!()` in message dispatch with `Err(PulsarError::...)`.

**When to use:** Any time an unhandled variant would otherwise panic the node process.

```rust
// In cosmwasm_msg_to_layer(), packages/app/src/wasm/keeper.rs
// BEFORE:
_ => todo!(),

// AFTER:
CosmosMsg::Stargate { type_url, .. } => {
    return Err(WasmError::UnsupportedCosmosMsg(format!(
        "Stargate message type_url={} is not supported", type_url
    )).into());
}
CosmosMsg::Any { type_url, .. } => {
    return Err(WasmError::UnsupportedCosmosMsg(format!(
        "Any message type_url={} is not supported", type_url
    )).into());
}
// NOTE: CosmosMsg is #[non_exhaustive] in cosmwasm-std 2.x,
// so the wildcard arm is still needed for future-proofing:
msg => {
    return Err(WasmError::UnsupportedCosmosMsg(format!(
        "Unsupported CosmosMsg variant: {:?}", msg
    )).into());
}
```

**Adding the error variant in `packages/app/src/wasm/error.rs` (or wherever `WasmError` is defined):**
```rust
#[error("Unsupported CosmosMsg: {0}")]
UnsupportedCosmosMsg(String),
```


### Anti-Patterns to Avoid

- **Do NOT use `std::sync::RwLock`** — gRPC handlers are async; `std::sync` locks will deadlock when held across `.await` points. Always use `tokio::sync::RwLock`.
- **Do NOT hold read lock across finalize_block** — write lock is required; any attempt to upgrade a read lock to a write lock will deadlock with tokio's RwLock (no lock upgrade).
- **Do NOT change App<T>'s internal API** — App methods do not need modification; only the wrapper lock type changes.
- **Do NOT add RwLock to Mempool** — Mempool is small and mutation-heavy; keep it as `Arc<Mutex<Mempool>>`.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Concurrent read/write segregation | Custom lock-free queue, custom sharding | `tokio::sync::RwLock` | Already a dep; correct semantics; no unsafe |
| Graceful error propagation | Catch-and-resume, `std::panic::catch_unwind` | `Result<_, PulsarError>` | Error types already exist; clean abort path |
| Stargate message forwarding | Implement Stargate dispatch | Return `Err(UnsupportedCosmosMsg)` | Out of scope; full Stargate requires IBC; Phase 02.2 goal is stability, not feature addition |

**Key insight:** `std::panic::catch_unwind` around VM calls would technically prevent a crash but would leave the App in an undefined state mid-`finalize_block`. The only correct fix is to prevent the panic from happening at all by converting `todo!()` to `Err`.

## Common Pitfalls

### Pitfall 1: RwLock Deadlock from Read-to-Write Upgrade Attempt
**What goes wrong:** A task holds a read guard, then tries to acquire a write guard. With `tokio::sync::RwLock`, the write lock waits for ALL read locks to release — but the task holding a read lock is blocked waiting for the write lock, causing deadlock.
**Why it happens:** The same async task acquires both locks in sequence.
**How to avoid:** Never hold a read guard while acquiring a write guard. Always release the read guard before acquiring the write guard. Use short-scoped lock acquisitions (`let result = { let app = self.app.read().await; app.method() };`).
**Warning signs:** The node hangs at startup or under the first block finalization.

### Pitfall 2: Stale InnerData After RwLock Migration
**What goes wrong:** `execute_block` (write path) advances the block height, but the previous read lock holder had cached the old `BlockInfo`. However, because reads acquire a snapshot and release immediately, there is no issue — each read lock call gets a fresh snapshot. The risk is if a sequence of operations (read info, do something, write) needs atomic consistency.
**Why it happens:** Misunderstanding that `RwLock` provides exclusive access for writes but not transactional atomicity for read-then-write sequences.
**How to avoid:** `check_tx` in `broadcast_tx` reads state and uses it locally — no write happens in this path. `finalize_block` only needs the write lock. These operations are correctly segregated.
**Warning signs:** Sequence number mismatches on concurrent BroadcastTx calls.

### Pitfall 3: Missing #[non_exhaustive] Wildcard in CosmosMsg Match
**What goes wrong:** Removing `todo!()` but not adding a wildcard arm. The compiler may produce a warning but still compile (CosmosMsg is non_exhaustive in cosmwasm-std 2.x), and a future contract using a new variant will panic again.
**Why it happens:** Thinking all variants are enumerated after adding Stargate/Any arms.
**How to avoid:** Always keep a final `msg => Err(UnsupportedCosmosMsg(...))` wildcard arm after explicit variant handling.

### Pitfall 4: Chain ID Lock in execute_block
**What goes wrong:** `execute_block` in `node.rs` currently acquires two separate read locks to get the `chain_id` (line 151) and then a write lock for `finalize_block` (line 189). If migrating to RwLock, this pattern is safe — read lock is released before write lock is acquired. But acquiring a read lock then a write lock in rapid succession (without releasing the read lock first) would deadlock.
**Why it happens:** The chain_id fetch and finalize_block call are sequential but the intermediate release must be explicit.
**How to avoid:** Scope the `chain_id` fetch in its own block: `let chain_id = { let app = self.app.read().await; app.info()... };` then separately acquire the write lock.

## Code Examples

### Example 1: Correct RwLock Usage in grpc.rs

```rust
// Source: tokio::sync::RwLock docs + existing grpc.rs patterns
use tokio::sync::RwLock;

pub struct LayerGrpcService<T: PersistentStorage + Send + Sync + 'static> {
    pub app: Arc<RwLock<App<T>>>,
    pub mempool: Arc<Mutex<Mempool>>,
    pub chain_id: String,
}

// Read path (query):
pub async fn handle_cosmos_query<T: PersistentStorage + Send + Sync + 'static>(
    app: &Arc<RwLock<App<T>>>,
    chain_id: &str,
    path: &str,
    body: Bytes,
) -> Result<Vec<u8>, Status> {
    let query = parse_cosmos_query(path, body, chain_id)
        .map_err(|e| Status::invalid_argument(e.to_string()))?;

    let response = {
        let app = app.read().await;  // SHARED read lock
        app.query(query)
    };  // lock released here

    let query_response =
        response.map_err(|e| Status::internal(format!("query failed: {e}")))?;
    encode_cosmos_response(query_response).map_err(|e| Status::internal(e.to_string()))
}
```

## Open Questions

1. **Do `CosmosMsg::Gov`, `CosmosMsg::Distribution`, `CosmosMsg::Ibc` also need explicit handling?**
   - What we know: These variants exist in CosmWasm 2.x and would also hit the `todo!()` / wildcard arm.
   - What's unclear: Are any contracts in the test suite or production use case sending these?
   - Recommendation: Handle them in the wildcard arm (same `UnsupportedCosmosMsg` error). Explicit arms only needed if we later want to implement them. Keep it simple.

2. **Should `check_tx` truly be read-only under RwLock?**
   - What we know: `check_tx` uses `ScratchTx::new(&reader)` — a throwaway transaction that never commits. The reader is obtained from `self.storage.reader()` which is a read-only snapshot. No App state is mutated.
   - What's unclear: Whether `ScratchTx` internally does any writes to the underlying storage (it should not, by design).
   - Recommendation: Confirm by reading `packages/storage/src/wrap/scratch_tx.rs` before coding. Based on the name and code at line 75 (`unimplemented!()`), it appears to be a read-only wrapper. Treat `check_tx` as safe for shared read lock.

3. **Is there a simpler alternative to RwLock — e.g., separate the query path from the app state entirely?**
   - What we know: The Cosmos SDK uses separate query routers with read-only storage snapshots for exactly this reason.
   - What's unclear: How deeply the `App<T>` query path is coupled to `InnerData` (which `finalize_block` mutates).
   - Recommendation: RwLock is the minimal-invasive fix. A separate read-only storage snapshot approach would be a larger architectural change, out of scope for this stability phase.
