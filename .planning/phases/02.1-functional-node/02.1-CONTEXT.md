# Phase 02.1: Functional Node - Context

**Gathered:** 2026-03-20
**Status:** Ready for planning

<domain>
## Phase Boundary

Get a working Layer node before Phase 3's Ethereum type migration: switch to real cross-process authenticated P2P consensus, wire a full gRPC interface (Cosmos SDK queries + tx submission + state sync streaming), implement the full transaction pipeline (submit → mempool → block → CosmWasm execute), and switch from MemoryStore to RocksDB persistence. This phase delivers a node that can actually run, communicate across processes, accept transactions, deploy and execute CosmWasm contracts, and persist state between restarts — the minimum viable baseline before the Ethereum type migration begins.

</domain>

<decisions>
## Implementation Decisions

### P2P Transport

- **Switch from `commonware_p2p::simulated` to `commonware_p2p::authenticated`** — the simulated transport is in-process only and cannot span OS processes; authenticated P2P uses TLS + Ed25519 identity keys and supports real multi-host networking
- **Peer discovery: static peer list in TOML config** — each node config has `[[peers]]` entries with `address = "host:port"` and `public_key = "ed25519_hex"`. No bootstrap discovery. Matches the static validator set model already established in Phase 2.
- **Reuse existing Ed25519 keys as P2P identity** — the key material JSON from `tools/generate-testnet-keys` already has `ed25519_private_hex`; authenticated P2P reads identity from the same file. No separate TLS cert files needed.
- **Peer address format**: `address = "IP:port"` + `public_key = "ed25519_pubkey_hex"` in `[[peers]]` table in node TOML config
- **Connection retry**: retry with exponential backoff until connected — nodes can start in any order, converge when all are up
- **TLS/cert strategy**: Claude's discretion — match whatever `commonware_p2p::authenticated` expects natively; don't add custom cert files
- **Unit tests**: keep existing simulated P2P unit tests (fast, no network), add a new authenticated P2P integration test that spins up real multi-process nodes
- **Testnet scripts**: update `scripts/testnet.sh` to launch real multi-process nodes with authenticated P2P that actually reach consensus across separate OS processes
- **Testnet topology**: localhost default (3 processes on one machine, different ports), plus a `docker-compose.yml` showing multi-host configuration

### gRPC Interface

- **Start a real tonic gRPC server** listening on `config.grpc_listen` alongside the consensus engine
- **Services to expose**:
  1. Cosmos SDK query services: bank (balance, all balances), auth (account), wasm (contract state, code info) — using existing handlers in `packages/cosmos/`
  2. `cosmos.tx.v1beta1.Service` — BroadcastTx endpoint for tx submission (sync mode)
  3. `layer.sync.v1` state sync streaming — wire existing `SyncProvider` impl from `packages/app/src/sync.rs`
- **Cosmos query handlers wired as-is** — do not start the Phase 3 type migration here; Phase 3 replaces Cosmos types throughout; clean separation of concerns
- **Shared state model**: `Arc<Mutex<App<T>>>` shared between gRPC server and consensus engine — consistent with the pattern already established in `LayerNode` and `LayerReporter`
- **gRPC server runs concurrently** with the consensus engine in the same tokio runtime

### Transaction Pipeline

- **Wire tx format: Cosmos proto tx format** (`cosmos.tx.v1beta1`) — the existing infrastructure in `packages/cosmos/tx.rs` parses this format. Phase 3 replaces it entirely; no need to invent something new for the transition period.
- **BroadcastTx: sync mode only** — returns after the tx passes the mempool check (`check_tx`). Block inclusion is asynchronous.
- **Full round-trip required**: submit tx via gRPC → `check_tx` in mempool → `drain_batch()` at propose time → deserialized `Vec<layer_std::Tx>` passed to `execute_block()` → `finalize_block()` executes CosmWasm msgs → state committed to RocksDB
- **Tx deserialization in `execute_block()`**: replace the `let txs: Vec<layer_std::Tx> = Vec::new();` stub (node.rs line ~153) with real deserialization from `BlockPayload` raw bytes
- **End-to-end success bar**: deploy the `contracts/root/` contract (StoreCode + InstantiateContract + ExecuteContract msgs), query resulting state — all via gRPC BroadcastTx with the tx included in a finalized block

### Storage Persistence

- **Switch from `MemoryStore` to `RockStore` (RocksDB)** — state persists between restarts; required for real node operation and for Phase 3's storage key migration testing
- **Single `data_dir` config field**: `data_dir = "./data"` in node TOML; app state stored at `{data_dir}/app/`, consensus WAL at `{data_dir}/wal/`
- **Remove `wal_path` as a separate top-level config field** — subsume into `data_dir`; wal path is `{data_dir}/wal/`
- **`layer-storage` `rocksdb` feature flag** enabled in `slay3rd/Cargo.toml`

### Claude's Discretion

- TLS/certificate handling for authenticated P2P — match Commonware's native expectations without custom cert files
- Exact retry backoff parameters for peer connection
- gRPC server thread-pool / task configuration
- Whether to keep `wal_path` as a computed subpath or add a separate override option
- Port allocation for the 3-node localhost testnet (e.g. P2P: 7001/7002/7003, gRPC: 9090/9091/9092)

</decisions>

<code_context>
## Existing Code Insights

### Reusable Assets
- `commonware_p2p::simulated` usage in `main.rs` (lines 410-465): the channel registration pattern (`oracle.control(pk).register(channel_id, quota)`) is likely similar for authenticated; the 3-channel model (vote=0, cert=1, resolver=2) stays the same
- `packages/cosmos/src/query.rs`: `parse_cosmos_query()` function handles bank/auth/wasm/cosmwasm queries — can be called from a tonic gRPC handler with minimal glue
- `packages/app/src/sync.rs`: `SyncProvider` trait with `current_state()` and `changes_since()` streaming methods already implemented on `App<T>` — just needs a tonic server wrapper
- `packages/cosmos/src/tx.rs`: Cosmos tx deserialization already exists — connects the gRPC BroadcastTx path to the mempool
- `layer-storage` crate: `RockStore` is gated behind `rocksdb` feature; `App<T>` is generic over `PersistentStorage` — switching from `MemoryStore` to `RockStore` is a type parameter change at the call site in `main.rs`
- `tools/generate-testnet-keys/src/main.rs`: already outputs `ed25519_private_hex` per node — no new tooling needed for P2P identity

### Established Patterns
- `Arc<Mutex<App<T>>>` passed to both `LayerNode` and `LayerReporter` — same pattern for gRPC server
- `commonware_runtime::tokio::Runner` wraps the async entry point — gRPC server should be spawned as a tokio task within `run_node()`
- `NodeConfig` uses `serde::Deserialize` from TOML — new `[[peers]]` array and `data_dir` field follow the same pattern
- `tools/generate-testnet-keys` outputs one JSON file per validator — the config structure for 3-node testnet should reference these files

### Integration Points
- The P2P replacement is isolated to `main.rs` lines 410-465 (P2P section + channel registration)
- gRPC server: new tokio::spawn in `run_node()`, after app init and before consensus engine start
- Tx deserialization: `node.rs` `execute_block()` method — replace `Vec::new()` stub with real deserialization; `BlockPayload` already stores raw bytes
- `NodeConfig` struct in `config.rs` — add `data_dir: String`, add `peers: Vec<PeerConfig>` (new struct with `address: String`, `public_key: String`); remove `p2p_listen` if it moves to a top-level field, or keep it; `wal_path` becomes computed from `data_dir`

</code_context>

## Specific Ideas

- User asked: "Should we investigate using commonware-storage?" — confirmed: `commonware-storage::QMDB` is the relevant candidate for Phase 6 (Merkle state roots / zkVM), not for application state storage in Phase 02.1. Note for Phase 6 planning.
- The `scripts/testnet.sh` script currently documents "Phase 3+ launch procedure" — Phase 02.1 promotes that to the real launch procedure.
- docker-compose.yml should show the multi-host model with real IP/port separation, even if the default testnet.sh runs on localhost.
- End-to-end test should exercise: `StoreCode` → `InstantiateContract` → `ExecuteContract` → gRPC query of contract state — using `contracts/root/` as the test contract.

</specifics>

## Deferred Ideas

- `commonware-storage::QMDB` as the Merkle state root / authenticated database for Phase 6 (ZKVM-01: sparse Merkle tree state root per finalized block) — worth investigating during Phase 6 planning as an alternative to rolling a custom SMT
- `commonware-storage::KV` traits as a potential future unification of the `App<T>` storage abstraction — nice-to-have, not urgent
- Dynamic validator set (resharing BLS shares) — Phase 02.1 keeps the static 3-node model from Phase 2; dynamic validator management is a later concern
- Multi-machine testnet automation (beyond docker-compose) — docker-compose covers the multi-host model; full cloud/k8s deployment is out of scope
