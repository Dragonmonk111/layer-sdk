  <action>
The determinism audit targets all code paths reachable from `App::finalize_block()` which will be called from `CertifiableAutomaton::certify()`. Any non-deterministic iteration will cause validators to produce different AppHash values, stalling the chain.

**File 1: packages/app/src/bank/keeper.rs**

1. Replace `use std::collections::HashMap;` with `use std::collections::BTreeMap;`
2. In `struct ValidCoins<'a>` (around line 529): change `seen: HashMap<&'a str, bool>` to `seen: BTreeMap<&'a str, bool>`
3. In `ValidCoins::new()` (around line 534): change `HashMap::new()` to `BTreeMap::new()`

NOTE: ValidCoins only uses `insert` and `contains_key` on the HashMap — iteration order is NOT used. However, replacing with BTreeMap is still correct because: (a) it costs negligible performance for small coin sets, (b) it eliminates any future risk if iteration is added, (c) it satisfies the CONS-04 audit requirement cleanly. The `seen` map is used to detect duplicate denoms during coin validation — duplicates cause an error, so the HashMap is not iterated over for consensus-affecting output.

**File 2: packages/app/src/wasm/vm/backend.rs**

1. Replace `use std::{collections::HashMap, fmt, mem::transmute};` with `use std::{collections::BTreeMap, fmt, mem::transmute};`
2. In `make_backend()` function (around line 55): change `iterators: HashMap::new()` to `iterators: BTreeMap::new()`
3. In `struct VmStore` (around line 336): change `iterators: HashMap<u32, Iter>` to `iterators: BTreeMap<u32, Iter>`
4. Any other `HashMap` references in this file must also be updated

NOTE: The VmStore iterators map is keyed by u32 iterator IDs. The iterator storage is used during WASM contract execution within `finalize_block()`. While the iteration over this map itself may not be consensus-critical (iterators are indexed by sequential u32 IDs), replacing with BTreeMap ensures consistent ordering if the map is ever iterated.

**File 3: packages/app/src/wasm/vm/cache.rs**

1. Replace `use std::{collections::HashSet, fmt};` with `use std::{collections::BTreeSet, fmt};`
2. In the `capabilities()` function (around line 40): change `HashSet<String>` return type to `BTreeSet<String>` and update the function body accordingly
3. Update any callers that expect `HashSet` — check the `cosmwasm_vm` API to see if `capabilities()` must return `HashSet`. If cosmwasm_vm requires `HashSet<String>`, convert at the boundary: `BTreeSet` -> `HashSet` only at the point where it's passed to the VM, and add a comment: `// DETERMINISM: capabilities maintained as BTreeSet internally; converted to HashSet at VM boundary`

IMPORTANT: If the cosmwasm_vm `Instance::new()` or similar function requires `HashSet<String>` in its signature, keep the `capabilities()` function returning `HashSet<String>` but add a `// DETERMINISM-SAFE: capabilities() is not called in certify/verify paths, only at VM instantiation` comment. The key question is whether `capabilities()` is called during `finalize_block()` — if it's called only during `cache.get_instance()`, it feeds into Wasmer's capability check, which is a structural validation (not iteration-order-dependent).
